2. DATABASE SCHEMA (4 TABLES)
================================================================================

solar_systems               One per user (UNIQUE user_id FK -> users)
  id (UUID PK)
  user_id (FK, UNIQUE, CASCADE DELETE)
  -- Step 1: panel info
  panel_type                Monocrystalline | Polycrystalline | Thin-film | Bifacial
  panel_qty (INTEGER >= 1)
  system_type               On-grid | Off-grid | Hybrid
  location (nullable)
  avg_monthly_bill (nullable, INR)
  -- Step 2: inverter (same row — UI steps 1+2 map to one API call)
  inverter_brand
  inverter_capacity_kw (>= 1)
  -- Onboarding state
  last_step                 furthest step completed (system/battery/grid/appliances/complete)
  appliances_configured     true once step-5 submitted
  is_complete               true after POST /complete
  completed_at (nullable)
  created_at / updated_at

battery_configs             One per system (UNIQUE system_id)
  Only for Off-grid / Hybrid
  battery_capacity_kwh (>= 1)
  backup_hours              CHECK IN (2, 4, 8)
  reserve_pct               CHECK BETWEEN 5 AND 50 (minimum SOC floor)
  Deleted automatically if system_type changes to On-grid

grid_configs                One per system (UNIQUE system_id)
  Only for On-grid / Hybrid
  meter_type                Net metering | Gross metering | No export
  sanctioned_load_kw (>= 1)
  tariff_type               Flat rate | Time-of-use | Slab-based
  discom (nullable)
  Deleted automatically if system_type changes to Off-grid

tracked_appliances          Many per system
  appliance_key             wash | heater | ev | pump | ac | fridge
  is_critical               true = never auto-off (UI "lock" toggle)
  UNIQUE(system_id, appliance_key)
  Replaced wholesale on each PUT /appliances (delete all + re-insert)

Why 4 tables not 1 JSON blob (interview answer):
  - battery_configs / grid_configs are NULL for irrelevant system types
  - DB CHECK constraints enforce valid backup_hours, reserve_pct, appliance_key
  - Easy to query "all Hybrid users with battery < 5 kWh" later
  - Clean cascade delete when user is removed

3. API ENDPOINTS (QUICK LIST)
================================================================================

All routes require: Authorization: Bearer <access_token>
Prefix: /onboarding

STEP ENDPOINTS (write)
  PUT  /onboarding/system       Step 1+2: panel + inverter (ALL system types)
  PUT  /onboarding/battery      Step 3: battery config (Off-grid / Hybrid ONLY)
  PUT  /onboarding/grid         Step 4: grid + tariff (On-grid / Hybrid ONLY)
  PUT  /onboarding/appliances   Step 5: appliance selection (ALL system types)
  POST /onboarding/complete     Finalise onboarding -> unlock dashboard

READ ENDPOINTS
  GET  /onboarding/status         Progress: steps_completed / required / remaining
  GET  /onboarding/summary        Full data dump for Review screen

Frontend note:
  After POST /auth/signup -> start onboarding (login skips it, goes to dashboard).
  GET /onboarding/status tells frontend which step to resume after page reload.

================================================================================
4. CONDITIONAL STEPS BY SYSTEM TYPE (CRITICAL FOR INTERVIEWS)
================================================================================

UI has 6 wizard panels but backend steps vary by system_type:

  On-grid  (5 steps):  system -> inverter -> [SKIP battery] -> grid -> appliances -> review
  Off-grid (5 steps):  system -> inverter -> battery -> [SKIP grid] -> appliances -> review
  Hybrid   (6 steps):  system -> inverter -> battery -> grid -> appliances -> review

Backend required steps for POST /complete:
  On-grid  : system + grid + appliances
  Off-grid : system + battery + appliances
  Hybrid   : system + battery + grid + appliances

Service guards:
  PUT /battery on On-grid  -> 422 system_type_conflict
  PUT /grid    on Off-grid -> 422 system_type_conflict
  Any step before system   -> 404 onboarding_not_found
  POST /complete twice     -> 409 onboarding_already_complete
  POST /complete missing steps -> 403 forbidden (lists missing step names)

system_type change side-effects (PUT /system re-submit):
  Hybrid  -> On-grid  : delete battery_configs row
  Hybrid  -> Off-grid : delete grid_configs row
  Off-grid -> On-grid : delete battery_configs row

5. REQUEST FIELDS BY SYSTEM TYPE
================================================================================

----------------------------------------
A) PUT /onboarding/system  (ALL types)
----------------------------------------
  panel_type            Monocrystalline | Polycrystalline | Thin-film | Bifacial
  panel_qty             integer >= 1
  system_type           On-grid | Off-grid | Hybrid
  location              string <= 200 (optional)
  avg_monthly_bill      decimal >= 0 INR (optional — NOT shown on review screen)
  inverter_brand        Fronius | SolarEdge | Growatt | Huawei FusionSolar | Other
  inverter_capacity_kw  decimal >= 1

----------------------------------------
B) PUT /onboarding/battery  (Off-grid / Hybrid ONLY)
----------------------------------------
  battery_capacity_kwh  decimal >= 1
  backup_hours          2 | 4 | 8
  reserve_pct           integer 5-50 (% — hard safety floor, never auto-drain below)

  On-grid: DO NOT SEND — returns 422

----------------------------------------
C) PUT /onboarding/grid  (On-grid / Hybrid ONLY)
----------------------------------------
  meter_type            Net metering | Gross metering | No export
  sanctioned_load_kw    decimal >= 1
  tariff_type           Flat rate | Time-of-use | Slab-based
  discom                string <= 100 (optional)

  Off-grid: DO NOT SEND — returns 422

----------------------------------------
D) PUT /onboarding/appliances  (ALL types)
----------------------------------------
  appliances: [
    { appliance_key: "wash"|"heater"|"ev"|"pump"|"ac"|"fridge", is_critical: bool }
  ]
  Empty list is valid. No duplicate appliance_key in one request.

  Appliance catalog (fixed enum, not free-text):
    wash   = Washing Machine  750 W
    heater = Water Heater      2000 W
    ev     = EV Charger        3300 W
    pump   = Pool Pump         900 W
    ac     = Air Conditioner   1500 W
    fridge = Refrigerator      150 W  (default is_critical=true in UI)

================================================================================
6. CODE WORKFLOWS (STEP BY STEP)
================================================================================

----------------------------------------
A) SAVE SYSTEM (Step 1+2)
----------------------------------------
1. Router validates SystemStepIn (Pydantic)
2. OnboardingService.save_system(user_id, data):
   - if no solar_systems row -> OnboardingRepository.create_system(...)
   - if exists -> update_system(...); handle system_type transition cleanup
3. last_step = "system"
4. get_db commits
5. Return 200 SolarSystemOut

----------------------------------------
B) SAVE BATTERY (Step 3)
----------------------------------------
1. _require_system() -> 404 if system step not done
2. Check system_type in {Off-grid, Hybrid} -> else 422 system_type_conflict
3. OnboardingRepository.upsert_battery(...) — create or update in-place
4. last_step = "battery"
5. Return 200 SolarSystemOut

----------------------------------------
C) SAVE GRID (Step 4)
----------------------------------------
1. _require_system() -> 404 if system step not done
2. Check system_type in {On-grid, Hybrid} -> else 422 system_type_conflict
3. OnboardingRepository.upsert_grid(...)
4. last_step = "grid"
5. Return 200 SolarSystemOut

----------------------------------------
D) SAVE APPLIANCES (Step 5)
----------------------------------------
1. _require_system() -> 404
2. OnboardingRepository.replace_appliances(...) — DELETE all + INSERT new list
3. appliances_configured = true, last_step = "appliances"
4. Return 200 SolarSystemOut

----------------------------------------
E) COMPLETE ONBOARDING
----------------------------------------
1. _require_system()
2. if is_complete -> 409 onboarding_already_complete
3. _missing_steps() compares required vs completed for this system_type
4. if any missing -> 403 forbidden with step names
5. is_complete=true, completed_at=now(), last_step="complete"
6. Return 200 OnboardingStatusOut

----------------------------------------
F) GET STATUS (resume wizard)
----------------------------------------
1. Load solar_systems by user_id (may be null)
2. Compute steps_required from system_type
3. Compute steps_completed from DB state:
     system     = solar_systems row exists
     battery    = battery_configs row exists
     grid       = grid_configs row exists
     appliances = appliances_configured == true
4. steps_remaining = required - completed
5. Return OnboardingStatusOut

----------------------------------------
G) GET SUMMARY (Review screen)
----------------------------------------
1. _require_system() -> 404
2. Eager-load battery_config, grid_config, appliances (selectinload)
3. battery=null for On-grid, grid=null for Off-grid
4. Return OnboardingSummaryOut grouped by section

7. TYPICAL FRONTEND FLOW (AFTER SIGNUP)
================================================================================

1. POST /auth/signup                          -> get access_token
2. GET  /onboarding/status                    -> know which step to show
3. PUT  /onboarding/system                    -> always first
4. IF Off-grid or Hybrid: PUT /onboarding/battery
5. IF On-grid  or Hybrid: PUT /onboarding/grid
6. PUT  /onboarding/appliances

9. ERROR SHAPE + STATUS CODES
================================================================================

Same shape as auth service:

  {
    "success": false,
    "error": {
      "code": "system_type_conflict",
      "message": "Battery configuration is not applicable for 'On-grid' systems."
    }
  }

Onboarding-specific codes:
  404 onboarding_not_found        step called before system step done
  422 system_type_conflict        battery on On-grid OR grid on Off-grid
  409 onboarding_already_complete POST /complete called twice
  403 forbidden                   /complete with missing required steps
  400 validation_error            Pydantic field validation
  401 invalid_token               missing/expired JWT

11. DESIGN DECISIONS (EXPECT THESE QUESTIONS)
================================================================================

Q: Why combine UI steps 1+2 (panel + inverter) into one API call?
A: Both fields live in the same solar_systems row. One PUT avoids partial
   state and matches the DB shape. UI can still show two wizard screens —
   frontend batches them into one request when step 2 is submitted.

Q: Why wholesale replace for appliances instead of PATCH?
A: Simpler — user's full selection is the source of truth. Delete all rows
   for system_id then bulk insert. No stale rows, no diff logic.

Q: Why store enums as VARCHAR not Postgres ENUM type?
A: Cheap migrations, works identically on SQLite test DB, enum owned by Python.

Q: Why separate battery_configs / grid_configs tables?
A: Conditional steps — On-grid users have no battery row at all (NULL join),
   not a row full of NULLs. CHECK constraints enforce valid ranges per table.

Q: What happens if user changes system_type mid-onboarding?
A: Service deletes now-irrelevant config (battery or grid) on PUT /system.
   Frontend should re-show the newly required step via GET /status.

Q: Why is avg_monthly_bill not in GET /summary?
A: Collected for future billing estimates but not displayed on Review screen
   in the current UI spec. Field is stored and returned in SolarSystemOut.

Q: How does onboarding relate to auth?
A: Completely separate module. Auth issues JWT; onboarding consumes it via
   get_current_user. No changes to any /auth/* endpoint or auth tables.

12. ONE-MINUTE ELEVATOR PITCH (MEMORIZE)
================================================================================

"I built a modular onboarding API as a vertical slice under app/modules/onboarding.
 After signup the user walks through a conditional wizard — On-grid skips battery,
 Off-grid skips grid, Hybrid needs both. Each step is a PUT endpoint guarded by
 system_type checks in the service layer. Data lives in four normalized tables
 with DB constraints. The service tracks progress via last_step and validates
 all required steps before POST /complete unlocks the dashboard. It reuses the
 existing JWT auth via get_current_user without touching the auth module."
