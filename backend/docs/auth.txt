2. DATABASE SCHEMA (4 TABLES)
================================================================================

users
  id (UUID PK)
  email (unique)
  hashed_password (NULLABLE)   <-- NULL = OAuth-only user, no password login
  is_active
  created_at

refresh_tokens
  id, user_id (FK)
  token_hash (SHA-256 of raw token)   <-- NEVER store raw refresh token
  expires_at (~7 days)
  revoked_at (NULL = active)
  created_at

auth_providers          <-- separate table so many providers can be linked later
  id, user_id (FK)
  provider ("google", later "github"...)
  provider_user_id (Google's "sub")
  UNIQUE(provider, provider_user_id)

password_reset_tokens
  id, user_id (FK)
  token_hash
  expires_at (~30 min)
  used_at (single-use)

Why auth_providers is separate (interview answer):
  - One user can link Google + GitHub later without schema change
  - Don't hardcode google_id column on users

3. API ENDPOINTS (QUICK LIST)
================================================================================

PASSWORD AUTH
  POST /auth/signup                  201 UserOut (no password)
  POST /auth/login                   access + refresh tokens (rate limited)
  POST /auth/refresh                 rotate refresh, new pair
  POST /auth/logout                  revoke refresh token (204)
  GET  /auth/me                      current user (Bearer access JWT)
  POST /auth/password-reset/request  always 204 (no email enumeration)
  POST /auth/password-reset/confirm  set new password via token

GOOGLE OAUTH
  GET  /auth/google/login            redirect to Google + set state cookie
  GET  /auth/google/callback         exchange code, login/link/create, tokens
  POST /auth/google/link-confirm     link when Google email not verified

HEALTH
  GET  /health

Frontend note:
  "Sign in with Google" and "Sign up with Google" BOTH hit /auth/google/login
  Backend decides signup vs login from whether user/link already exists.

4. CODE WORKFLOWS (STEP BY STEP)
================================================================================

----------------------------------------
A) SIGNUP (email + password)
----------------------------------------
1. Router validates UserCreate (email, password min 8)
2. AuthService.signup:
   - if email exists -> 409 email_already_registered
   - hash password with bcrypt
   - UserRepository.create(email, hashed_password)
3. get_db commits
4. Return 201 UserOut (id, email, is_active, created_at) — never password

----------------------------------------
B) LOGIN
----------------------------------------
1. Rate limit: 5/minute (slowapi)
2. AuthService.login:
   - find user by email
   - if missing OR hashed_password is NULL OR wrong password OR inactive
     -> SAME 401 "Incorrect email or password"  (no user enumeration)
   - TokenService.issue_token_pair(user_id)
3. Return { access_token, refresh_token, token_type: "bearer" }

----------------------------------------
C) TOKEN PAIR (how tokens work)
----------------------------------------
ACCESS TOKEN (JWT, ~15 min)
  - Signed HS256 with JWT_SECRET_KEY
  - Payload: sub=user_id, type=access, iat, exp, jti
  - Sent as: Authorization: Bearer <token>
  - Used by get_current_user for /me and protected routes
  - NOT stored in DB (stateless)

REFRESH TOKEN (opaque random string, ~7 days)
  - secrets.token_urlsafe(64) generated
  - ONLY SHA-256 hash stored in refresh_tokens table
  - Raw token returned to client once
  - Used only on /auth/refresh and /auth/logout

Why hash refresh tokens?
  DB leak alone cannot reuse refresh tokens.

----------------------------------------
D) REFRESH (rotation)
----------------------------------------
1. Client sends raw refresh_token
2. Hash it, look up in DB
3. If missing / expired / revoked:
   - if already revoked (reuse) -> revoke ALL user sessions (theft signal)
   - raise 401 invalid_token
4. Revoke old token (set revoked_at)
5. Issue NEW access + NEW refresh pair
6. Old refresh can never be used again

Interview keyword: "refresh token rotation + reuse detection"

----------------------------------------
E) LOGOUT
----------------------------------------
1. Hash refresh token, find row
2. Set revoked_at = now
3. Idempotent (already revoked = still 204)
4. Access token still valid until expiry (short-lived by design)
   Optional future: access token blacklist / shorter TTL

----------------------------------------
F) GET /me (protected)
----------------------------------------
1. Depends(get_current_user)
2. Parse Bearer header
3. jwt.decode (signature + expiry)
4. type must be "access"
5. Load user by sub UUID
6. If missing/inactive -> 401
7. Return UserOut

----------------------------------------
G) PASSWORD RESET
----------------------------------------
REQUEST:
  - Always return 204 even if email unknown (no enumeration)
  - If user exists: create opaque token, store hash, expire in 30 min
  - STUB: print token (would email in production)

CONFIRM:
  - Hash token, find row
  - Must be unused and not expired
  - Set new bcrypt password
  - Mark used_at (single-use)

----------------------------------------
H) GOOGLE OAUTH FULL FLOW
----------------------------------------
1. GET /auth/google/login
   - Generate random state
   - Set httponly cookie oauth_state
   - Redirect to Google consent URL (openid email profile)

2. User approves on Google

3. GET /auth/google/callback?code=&state=
   - Compare state cookie vs query (CSRF protection) — secrets.compare_digest
   - GoogleOAuthClient.fetch_user_info(code):
       a. POST code to Google token endpoint
       b. Get id_token
       c. Verify signature via Google JWKS (RS256)
       d. Check aud == GOOGLE_CLIENT_ID
       e. Check iss is Google
       f. Extract sub, email, email_verified, name
   - OAuthService.authenticate(info):

       IF provider+sub already linked  -> issue tokens for that user

       ELSE IF no user with that email -> create user (password=NULL),
                                           create auth_providers link,
                                           issue tokens   (= SIGN UP)

       ELSE IF email exists AND email_verified=true
                                           -> auto-link Google to existing user,
                                           issue tokens   (= SIGN IN + LINK)

       ELSE IF email exists AND email_verified=false
                                           -> 403 oauth_link_confirmation_required
                                           + short-lived link_token JWT
                                           (do NOT auto-link — account takeover risk)

4. POST /auth/google/link-confirm (edge case)
   - Decode link_token
   - User proves password on existing account
   - Then create auth_providers link + issue tokens

Provider-agnostic design:
  OAuthProviderClient interface + GoogleOAuthClient
  Adding GitHub = new client + router, same OAuthService linking policy

5. SECURITY CHECKLIST (SAY THESE IN INTERVIEW)
================================================================================

[ ] Passwords: bcrypt via passlib — never store/log plaintext
[ ] Access JWT: HS256, short-lived (~15 min), secret from env
[ ] Refresh: opaque, hashed (SHA-256) in DB, rotated on use
[ ] Reuse of revoked refresh => revoke ALL sessions for that user
[ ] Login / reset request: rate limited (slowapi)
[ ] Login errors: generic message (no email existence leak)
[ ] Signup duplicate: 409
[ ] CORS: explicit origins only (never "*") with credentials
[ ] Secrets only in .env (DATABASE_URL, JWT_SECRET, Google keys)
[ ] OAuth: verify ID token signature + aud + iss server-side
[ ] OAuth: state cookie prevents CSRF on callback
[ ] Never auto-link OAuth unless email_verified=true
[ ] OAuth-only users: hashed_password=NULL => password login disabled
[ ] Error shape always: {"success":false,"error":{"code":"...","message":"..."}}

10. SECURITY TRADE-OFFS (EXPECT THESE QUESTIONS)
================================================================================

Q: Why HS256 not RS256?
A: This service both issues and verifies tokens. HS256 is simpler.
   Switch to RS256 later if other microservices must verify without sharing secret.

Q: Why PyJWT not python-jose?
A: python-jose is poorly maintained / had CVEs. PyJWT is standard + has JWKS client.

Q: Why SHA-256 for refresh tokens, bcrypt for passwords?
A: Refresh tokens are high-entropy random (fast hash OK).
   Passwords are low-entropy human strings (need slow KDF = bcrypt).

Q: Why not blacklist access tokens on logout?
A: Access tokens are short-lived (15 min). Refresh is revoked immediately.
   Blacklist adds Redis complexity; acceptable trade-off for this design.

Q: Why SQLite in tests?
A: Speed + zero external deps. Models avoid Postgres-only features via GUID type.
   Production still Postgres (Neon/local).

Q: Why in-memory rate limit?
A: Fine for single process. Multi-instance needs Redis-backed limiter.

11. ONE-MINUTE ELEVATOR PITCH (MEMORIZE)
================================================================================

"I built a production-style FastAPI auth service with layered architecture:
 routers -> services -> repositories -> models. Password signup/login uses
 bcrypt and issues a short-lived JWT access token plus a hashed, rotated
 refresh token. Google OAuth uses OpenID Connect with ID-token verification
 and a provider-agnostic auth_providers table so we can add GitHub later.
 Account linking only auto-links when Google reports email_verified; otherwise
 the user must confirm with their password. Security includes generic login
 errors, rate limiting, CSRF state on OAuth, and consistent error responses.
 Config is env-driven so we can switch Neon cloud Postgres to local without
 code changes."
